# Threads 저장 게시물 → Obsidian 자동 백업

## 적용 범위

Chrome 빌드 `1.4.3-chrome.6`부터 지원한다. X 기능과 저장 파일 이름은 그대로 유지한다.
`../threadmark/content.js` 및 DOM·이미지 추출 관련 해결 기록을 참고했다.
참고 저장소는 수정하지 않았으며 코드를 통째로 복사하지 않고 별도 TypeScript 수집기를 구현했다.

`threadmark`의 전체 페이지 추출 방식은 저장 목록의 서로 다른 작성자·이미지를 섞을 수 있어 사용하지 않았다.
`[dir="auto"]`를 사용하되 게시물 고유 링크와 카드 경계를 기준으로 내용을 분리한다.
프로필 이미지·인용 카드·추천 사이드바를 제외하고, 같은 글이라도 고유 코드가 다르면 각각 보관한다.
짧은 글을 길이 기준으로 버리지 않는다. 사진만 있고 본문이 없는 글도 미디어 URL을 저장한다.

## 사용 방법

1. `chrome://extensions`에서 Twitter Web Exporter를 새로고침한다. 권한 변경 확인이 나오면 Threads 접근 범위를 검토한다.
2. 기존 X·Threads 탭과 백업 설정 탭을 새로고침한다.
3. Obsidian 자동 백업 설정에서 기존 API 연결을 확인한다. 저장된 API 키·폴더는 재사용한다.
4. `자동 백업 사용`과 `Threads 저장 게시물도 자동 백업`을 켜고 `백업 설정 적용`을 누른다.
5. `https://www.threads.com/saved`를 열고 게시물이 로드되도록 천천히 스크롤한다.
6. 접힌 원문은 상세 페이지에서 더 보기를 펼친다. 저장 목록에서 먼저 수집한 원문에 한해 상세 내용이 추가 반영된다.

Chrome 빌드 `1.4.3-chrome.7`부터 작은 상태 창 대신 X와 같은 형태의 **Web Exporter** 제어판이
Threads 페이지 왼쪽 위에 표시된다. 홈·저장 목록·게시물 상세·프로필에서 사용할 수 있다.
북마크·댓글/대댓글 수, 이번 탭의 백업 요청 수와 실행 로그를 보여준다.
행의 화살표는 로컬 수집 목록(작성자·본문·ID 검색, 25개씩 페이지 이동) 또는 Obsidian 설정을 연다.
톱니바퀴에서는 테마·언어와 Obsidian 백업 설정을 열 수 있다. Threads 툴바의 설정 버튼도 활성화했다.
닫기 상태는 스크롤·페이지 이동·새로고침 후에도 유지되며 왼쪽 고양이 버튼 또는 툴바에서 다시 연다.
제어판 표시·테마·언어는 Threads 사이트의 로컬 설정이며 X 설정과 분리된다.
제어판 내부 링크/본문은 수집에서 제외한다. 홈·프로필 표시가 해당 피드 수집을 허용하는 것은 아니다.
`다시 수집` 또는 백업 설정의 `기존 수집 데이터 추가`로 캐시된 저장 게시물을 다시 제출한다.
대기열 제출 수는 볼트 파일 쓰기 성공 수가 아니다. 실제 저장 결과는 Obsidian 백업 설정에서 확인한다.
업데이트만으로 Threads 자동 백업을 임의 활성화하지 않는다. 새 체크박스 기본값은 꺼짐이다.

## 파일 구조

설정한 백업 폴더 아래 `threads/`에 분리한다. 기본 예시는 다음과 같다.

```text
raw/articles/twitter-web-exporter/
  x-<X 게시물 ID>.md
  threads/
    threads-<코드의 UTF-8 hex>.md
    revisions/threads-<코드의 UTF-8 hex>-<본문 SHA256>.md
```

Threads 코드는 대소문자를 구분한다. macOS의 대소문자 비구분 파일시스템에서 충돌하지 않도록
고유 코드를 원복 가능한 소문자 hex로 인코딩한다. 실제 Threads 숫자 API ID로 변환한 것은 아니다.
원래 고유 코드와 읽기 쉬운 원문 링크는 `source_id`, `source_url`에 보존한다.
`source_platform: threads`, 작성자, 게시 시각(확인된 경우), 출처, 본문 해시와 수집 상태를 기록한다.

같은 내용은 중복 저장하지 않는다. 바뀐 내용은 전체 묶음을 `revisions/`에 저장하고 최초 파일은 보존한다.
기존 확장 프로그램의 REST 전송·확인·재시도 큐를 공유하되 작업 키와 파일 경로는 X와 구분한다.
API의 PUT에는 생성 전용 원자성 보장이 없으므로 다른 도구가 같은 파일을 동시에 수정하지 않도록 한다.

## 댓글 및 수집 한계

- 자동 스크롤·미로드 게시물 추가 조회·Threads 내부 API 호출을 하지 않는다.
- 댓글은 DOM에 실제 게시물 URL을 가리키는 `Replying to` 또는 `답글 대상` 링크가 있고,
  저장 원문까지 부모 관계가 이어지는 경우에만 합친다. 같은 화면에 있다고 댓글로 추정하지 않는다.
- 이 관계가 노출되지 않는 Threads 화면에서는 댓글을 합칠 수 없다. 전 댓글 수집 완료를 주장하지 않는다.
- 접힌 본문은 표시를 남기며, 더 긴 본문을 이미 수집했다면 이후 접힌 목록이 그 본문을 지우지 않는다.
- Threads DOM이 바뀌거나 카드 경계를 찾지 못하면 수집이 제한될 수 있다. 이때 화면에 안내한다.
- 미디어는 URL만 저장한다. URL이 만료되거나 원본이 삭제되면 이미지를 다시 열지 못할 수 있다.
- 소스 캐시는 같은 Threads origin·브라우저 프로필의 IndexedDB를 사용한다. 계정별 분리는 하지 않는다.
- Threads 소스 캐시 10,000개, 묶음 댓글 1,000개·4 MiB, 공통 대기열 5,000개 한도가 있다.

API 키는 기존 trusted extension storage만 사용한다. Threads 코드에는 키 조회·설정 변경 권한이 없다.
볼트의 Git·클라우드 동기화 제외 규칙은 변경하지 않았다. Threads 하위 폴더도 비공개 범위를 확인해야 한다.

## 실제 저장 목록 수집 실패 수정 — chrome.8 (2026-09-23)

증상: Web Exporter는 보이지만 북마크 0개이며 분리되지 않은 게시물 링크 경고가 반복됨.
원인: 실제 저장 목록의 시간 permalink가 `span[dir="auto"]` 내부에 있었지만,
기존 ownLinks는 dir=auto 내부의 링크를 모두 제외했다. main/article 태그도 없는 레이아웃이었다.
또한 시간 문자열·주제 링크를 본문으로 오인하면 카드 전체가 아닌 헤더에서 탐색이 끝날 수 있었다.

- 시간 링크 및 단독 permalink 래퍼를 허용하고, 본문 문장에 삽입된 다른 게시물 링크는 분리 기준에서 제외.
- 해당 작성자 링크와 permalink의 공통 헤더를 식별해 시간·사용자명·주제 메타데이터를 본문에서 제외.
- 실제 본문과 형제 미디어 영역을 포함하는 카드에서 추출. 프로필 사진·인용·제어판은 계속 제외.
- 같은 게시물의 반복 링크는 분리 실패 수에서 중복 계산하지 않음.
- 출처 작성 시각은 해당 permalink와 그 헤더에 속한 time 요소에서 읽음.

실제 로그인한 저장 목록의 DOM을 읽기 전용으로 검사했다. 수정 추출기 결과는 원문 4개,
분리 실패 0개, 게시물별 미디어 URL 1/4/2/1개였다. 해당 검사로 브라우저 DB나 볼트에 쓰지 않았다.
테스트 자료에는 사용자명·게시물 본문·URL·미디어 주소를 치환한 구조만 저장했다.
`tests/fixtures/threads-saved-live-anonymized.html` 및 `tests/threads-live-dom.spec.ts`가 회귀 사례다.
기존 Threads 통합 테스트의 permalink도 동일한 dir=auto 래퍼로 변경해 수집→REST 저장 경로를 검증했다.
`pnpm check:chrome`: 타입 검사·린트·Chrome 빌드·44개 테스트 통과.
업데이트 적용은 확장 프로그램 새로고침 후 기존 Threads 탭 새로고침이 필요하다.
